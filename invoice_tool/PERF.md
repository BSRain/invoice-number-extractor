# v1.1 性能记录

瓶颈：已读取号码的低置信度照片仍触发四次整页 OCR。方向重试无法可靠修复模糊数字，应保留待复核状态。

本机同一张样例照片，原版与新版交替运行，各次创建新 Reader，包含模型首次加载。单独比较旋转退出条件；没有更改模型、线程数、图片尺寸或置信度阈值。

| 试验 | 原版 | 新版 | 结果 |
| --- | --- | --- | --- |
| 第 2 轮 | 31.81 秒，4 次 OCR | 8.45 秒，1 次 OCR | 号码、代码、状态、方向相同 |
| 第 3 轮 | 40.37 秒，4 次 OCR | 9.30 秒，1 次 OCR | 号码、代码、状态、方向相同 |
| 两轮中位数 | 36.09 秒 | 8.88 秒 | 耗时下降约 75%，保留 |

第 1 轮原版与单元测试短暂同时运行，不计入上述中位数。前后差异远大于两轮波动，但仍只代表这张照片在本机的表现，不能推广到所有发票。原始计时保存在本地 `output/invoices/performance_comparison.json`，不提交真实业务数据。

同一窗口后续批次复用 OCR 模型：界面烟雾测试验证停止事件重置、模型对象不变、第二批实际 OCR 号码正确。首次启动仍需加载模型，不承诺消除 OCR 本身的耗时。

页头裁剪和并行 OCR 本次未采用：整页输入可以保留下方其他发票，当前先解决已测出的重复识别瓶颈。旋转票、没有清晰页头、候选冲突或缺失号码仍沿用完整重试。后续若增加裁剪，需要单页多票布局测试和独立计时。

回归门槛：既有号码、代码、状态、方向不变；低分号码仍待复核；同页下方发票不丢失；Excel 汇总与明细保留全部结果，前导零与 20 位号码按文本保存。用全部原始样例及实际 OCR、界面烟雾测试验证，不能只依据耗时通过。

# v1.2 继续优化

分段计时显示样例照片中文字识别约占 65%–75%，方向分类约 0.06–0.09 秒。优化单次识别而非取消分类。

| 尝试 | 比较 | 结论 |
| --- | --- | --- |
| 推理线程 2 → 4 | 同图、模型预热、六轮交替；中位数 4.241 → 3.362 秒；2 线程范围 4.187–4.377，4 线程范围 3.275–3.693 | 快约 21%，六轮均改善且两个范围不重叠，保留；不超过本机逻辑 CPU 数 |
| 识别 batch 6 → 16 | 2 线程预热读图 3.81 → 5.77 秒；4 线程 2.97 → 5.44 秒 | 明显变慢，保留原 batch=6，不采用 16 |
| 一页一票票头 OCR | 同一 4 线程 Reader、预热后清除结果缓存；3 页旋转扫描件两轮交替：标准 18.974 / 19.794 秒，快速 7.799 / 7.301 秒 | 中位数 19.384 → 7.550 秒，耗时减少约 61%，各号码、代码、状态和方向一致，保留为显式选项 |
| 有界内存内容缓存 | 17 份输入、25 条结果再次读取约 0.033 秒，17 次缓存命中，结果字段与首次读取相同 | 保留；内容 SHA-256 匹配，最多 32 份 / 200 条，不缓存失败或中断文件，不存磁盘 |

以上是本机具体样例表现，不作为任意设备/文件的固定比例。第一次加载模型不包含在预热比较里。原始分段、线程及票头计时位于本地 `output/invoices/`，真实业务数据不提交 Git。

快速模式按用户选择的“一页一票”约定识别上方 40% 区域，无法证明下方没有第二张票。因此默认关闭，并在界面明确提示。同页多票沿用完整识别；疑难号码、多个候选、低分、传统代码缺失或裁剪异常回退整页，回退页可能比标准模式更慢。裁剪框坐标映射回完整票面，用于预览及复核。

默认和快速模式分别检查全部 25 条用户样例，号码、代码、状态、方向均与 v1.1 基线一致，快速模式直接完成其中 7 页 OCR，其余使用文字层或回退。整批验证曾与其他任务短暂交叠，因此不采用整批计时作提速结论；采用上面的独立交替测试。

缓存以内容与模式为键，先复制原始结果再交给界面，文件读取前后检查内容，改变文件及同名同长度且恢复时间戳仍重新识别。缓存超限按 LRU 淘汰，大文件超过记录限额继续输出所有结果但不缓存。仅当前进程复用；再次导入已见路径需先清空界面结果。

文件级并发本版未增加：当前已验证的改进来自推理线程、票头路径和内容复用。以后评估两文件并行应使用独立读取器/模型，并单独比较吞吐与内存，不能据此版本的结果宣称已实现并行文件处理。


# v1.3 票头区域优化

同一模型预热后，新旧 Reader 交替识别相同的三页旋转扫描件，逐轮清空内容缓存；保持线程、模型、置信度和原图清晰度不变。

| 尝试 | 三轮测量 | 结论 |
| --- | --- | --- |
| 大票头先缩小至宽 1400，再按需高清复核 | 原版 12.753 / 10.840 / 9.757 秒；试验版 17.015 / 15.749 / 11.664 秒，中位数 10.840 → 15.749 | 重试增加，总体更慢，撤销 |
| 大图先识别原清晰度上方 25%，失败恢复 40% 票头 | 原版 10.149 / 9.677 / 9.439 秒；新版 7.155 / 5.221 / 6.281 秒，中位数 9.677 → 6.281，约减少 35% | 三轮均改善、区间不重叠；每页号码、代码、状态和方向相同，保留 |

仅显式一页一票快速模式且校正后宽度超过 1400 像素启用。完整 8/20 位号码通过原 .96 阈值，传统票还必须读取可靠代码；多候选、低分、缺失标签或代码不直接接受。已读到带标签的完整号码但低分或代码不可靠时直接整页，避免额外票头重试；未读到完整号码或冲突时再尝试原 40% 票头，然后按需整页。疑难页仍可能变慢。默认模式和同页多票流程保持完整识别，缓存仍仅在内存中。

以上是本机特定样例的收益，不代表整个批次或所有文件都减少 35%。原始对照计时保存在本地 output/invoices/v13_benchmark.json，未提交真实业务数据。跨启动缓存和文件并行尚未启用。

全部 25 条原始样例：号码、代码、状态、方向与 v1.2 一致，无差异；两张 Excel 表均保留全量结果。42 项单元测试覆盖原流程及新增高清区域坐标、缺失号码恢复原票头、低分/缺失代码直接整页、取消不继续识别。整批验证计时受其他检查交叠影响，不用来宣称整批提速。


# v1.4 复用方向检测文字框

瓶颈：v1.3 先整页检测判断方向，再对票头做第二次文字检测。单票快速路径现在将首次检测得到的四边形变换到预览方向，直接用原图裁剪文字行，沿用方向分类（包含 180 度纠正）和 batch=6 的识别模型；成功路径不再检测票头。仅锁定 RapidOCR 1.4.4 的组件适配器调用 get_crop_img_list / text_cls / text_rec，接口不兼容时恢复原路径，升级依赖必须重新验收。参考 [RapidOCR 1.4.4 官方接口和源码入口](https://rapidai.github.io/RapidOCRDocs/v1.4.4/install_usage/api/RapidOCR/)；实现前核对了本机锁定版本的 main.py、TextClassifier 和 TextRecognizer 源码。

| 试验 | 原版 → 新版 | 结论 |
| --- | --- | --- |
| 三页旋转扫描件，三个交替轮次 | 原版 3.985 / 3.862 / 4.009 秒；新版 3.386 / 3.447 / 3.198 秒；中位数 3.985 → 3.386，耗时约下降 15% | 同一预热模型、逐轮清空缓存，无其他 OCR 测试同时运行；三轮均改善，两个区间不重叠，保留 |
| 三页扫描件加一张低质量照片，两个交替轮次 | 原版 11.140 / 10.290 秒，检测各 9 次；新版 10.896 / 9.456 秒，检测各 6 次 | 全部四条号码、代码、状态、方向一致；范围重叠，不能据此宣称混合批次有固定提速比例。失败复用可能增加识别尝试 |

默认整页模式不使用该路径。快速模式接受门槛仍为 .96，传统票代码仍需可靠；低分完整号码直接回退整页，缺失/冲突或组件错误恢复原票头流程。非法/越界/退化框不接受，跨越裁剪下边界的文字不截半识别，取消后不继续分类或识别。文字框依原顺序关联批量输出，返回预览方向的完整页归一化坐标；不对数字猜测或补齐。

51 项单元测试通过。全部 25 条用户样例的号码、代码、状态和方向与 v1.3 一致，仍只有 7 页由快速模式完成，其余使用文字层或回退；不以整批验收计时作提速声明。原始计时、真实业务结果均保留本地 output/invoices，不提交 Git。界面合成旋转票还检查实际检测模型只调用一次、复核/取消/缓存和 Excel 全量字符串输出。

# v1.5 文件并行与调度

新增显式两个文件并行，默认关闭；单文件仍走原串行路径。PyMuPDF 官方明确不支持多线程，因此使用独立 spawn 进程，每个进程自行打开 PDF 和保存 OCR 模型。Windows 便携入口在解析参数和创建界面之前调用 `freeze_support()`。路径和结果通过队列传递，不跨进程传 PDF 对象或渲染页。

调度先检查两个进程的结果，哪个空闲就领取下一文件，不等待前一个文件显示完毕。输出仍按输入和页码顺序。有界窗口最多提前调度 4 份，每份暂存至多 8 条，各进程输出队列至多 8 条，界面队列至多 128 条；多页文件边读边输出。停止不再派发新文件，排空已经开始任务的部分结果，再复用进程处理后续批次；已完整结束的文件与部分文件分开标记。任务异常保留失败记录；进程异常及中断迭代清理全部子进程。

本机为 16 个逻辑 CPU。最初每进程 2 个推理线程的混合扫描 PDF / 照片试验没有稳定收益，不采用此配置作为本机默认。最终每次模型推理最多 4 线程，且不超过 CPU 数的一半（至少 1）；各子进程的 OpenCV 预处理设为 1 线程，避免其默认每进程 16 线程再叠加模型线程。限制 OpenCV 后，照片仍没有稳定加速，不能单独把线程限制宣称为延迟优化。

最终配置与原串行 Reader 对比：同一输入、同一模式和置信度，先分别跑一轮预热，再三轮交替运行；每次读取清空内容结果缓存，逐轮比对来源、页码、号码、代码、状态和方向。

| 输入 | 串行预热后三轮 | 并行预热后三轮 | 结论 |
| --- | --- | --- | --- |
| 3 份扫描 PDF，共 7 页，单票快速模式 | 11.116 / 11.915 / 11.248 秒，中位数 11.248 | 9.813 / 9.905 / 9.547 秒，中位数 9.813 | 中位数耗时下降约 13%，三轮均改善且区间不重叠；字段相同，保留显式并行功能 |
| 3 张高清照片，单票快速模式 | 14.955 / 14.770 / 16.064 秒，中位数 14.955 | 15.977 / 14.911 / 15.178 秒，中位数 15.178 | 范围重叠，没有稳定收益；照片不承诺提速 |

首轮含模型与进程初始化，扫描 PDF 串行 15.275 秒、并行 14.294 秒，照片串行 21.999 秒、并行 21.206 秒，不能外推为首次启动的固定收益。以上仅代表本机和这些样例，纯文字 PDF、较少文件或 CPU / 内存紧张时可能更慢。

内存是明确代价。测试同时保留串行模型与两个并行进程：扫描 PDF 首轮工作集总和 187.6 → 505.2 MiB，后续交替批次最高约 870.9 MiB；照片 126.8 → 377.1 MiB，之后约 377 MiB。此数字不是软件内存上限，PDF 解码缓存及模型运行库也占内存，有界结果队列不能限制其内部缓存。并行每进程的结果缓存为 16 份 / 100 条，串行缓存独立保留；只在进程内复用副本内容，退出释放。

原始含业务数据的计时仅保存在本地 `output/invoices/v15_pdf_benchmark.json` 和 `v15_bounded_benchmark.json`，不上传。回归要求仍为全部样例字段与重复序号不变、两个 Excel 表保留全部行且号码为文本，以及合成实际 OCR 的 GUI / 便携双进程验证。

最终验证：59 项 unittest 通过；源码 GUI、便携 GUI 的合成双进程 OCR、复核、旋转、进程复用和 Excel 均通过，并单独检查测试窗口布局。便携版从解压目录运行，去掉 PYTHON 环境变量、PATH 仅保留 Windows 路径；标准及快速模式分别用两个进程读取全部 25 条用户样例，号码、代码、状态、方向和重复序号与 v1.4 基线一致，两个 Excel 表均为 25 条数据且号码单元格保持文本。未在全新 Windows 电脑验证。

# v1.6 按已确认的缓存分配任务

v1.5 空闲进程领取下一文件，已识别内容的副本可能被另一进程重复 OCR。新增最多 32 个内容指纹的归属提示；结束每个任务时，进程报告实际缓存键及命中次数，父进程删除已淘汰的提示，只给已缓存内容选择对应进程。后续批次调换文件顺序也能复用，原有来源和输入顺序不变。窗口内另一个进程可以先处理其他文件。模型、结果缓存及其容量仍在各进程，传输的只有路径、结果和少量指纹元数据。

提示按 SHA-256、后缀和模式匹配，Reader 在执行时独立重新校验实际内容；指纹读取后改变文件也不能误用旧结果。停止不启动尚未分配的副本，部分文件仍可重试。失败、取消和超过缓存容量的文件不被报告为已缓存，首次文件仍正常并行；清理进程同时清理提示和命中计数。额外读取指纹会增加 I/O，因此不能承诺全部新内容的批次更快。

试验过强行等待首次识别的同内容文件，使首批副本只 OCR 一次，但超过 100 条不能缓存的文件、失败文件会退化为串行。未保留该方案；最终仅使用进程报告的真实缓存归属。

交替比较 v1.5 与 v1.6：使用一张用户照片转成 PNG，按轮次改变票面外一个像素产生新内容；每轮先让两个进程读取两个不同内容，再换文件名、调换顺序导入两份相同内容副本。前后模式、模型、线程和置信度相同。第一轮预热不计入比较；三轮均核对号码、代码、状态、方向，且根据实际读取计数验证缓存命中。

| 副本重新导入 | 三轮耗时 | 中位数 | 实际 OCR |
| --- | --- | --- | --- |
| v1.5 | 8.944 / 9.899 / 9.654 秒 | 9.654 秒 | 每轮两次 |
| v1.6 | 0.047 / 0.032 / 0.051 秒 | 0.047 秒 | 每轮零次，两份来源都保留 |

该差异来自避免重复 OCR，仅适用于仍在同一窗口对应模式缓存内的相同内容副本，不是首次识别加速比例。退出、内容改变、模式切换、失败或容量淘汰仍须读取。原始含业务数据的计时只保存在本地 `output/invoices/v16_benchmark.json`，不提交 Git。

最终验证：68 项 unittest 通过，移除缓存归属分配的实验改动被调换副本顺序的回归测试拒绝，随后恢复正式实现。源码及解压后的便携 GUI 都验证实际双进程 OCR、后续批次两次真实缓存命中、来源与顺序、复核、旋转和 Excel。便携程序去掉 PYTHON 环境变量、PATH 仅保留 Windows 路径，标准和快速模式各用两个进程读取全部 25 条用户样例；号码、代码、状态、方向和重复序号与 v1.4 基线无差异，两张 Excel 表均保留全部 25 条数据，号码单元格为文本。包内源码与最终实现匹配；未在全新 Windows 电脑验证。
